# Part 6: Evaluation & Failure Analysis

## Overview

Part 6 extends the RAG pipeline by introducing a lightweight, transparent evaluation runner to measure and compare retrieval configurations. It avoids complex external dependencies (like RAGAS) to maintain a fast, focused feedback loop.

## Evaluation Dataset

The dataset is maintained as a static JSON file (`data/evaluation/eval_cases.json`). 
Each test case contains:
- `id`: Stable identifier for the test case
- `question`: The user query
- `expected_chunk_ids`: The exact chunk IDs (ground truth) that completely support the answer
- `expected_policy_ids`: The policy identities that must be cited
- `answerability`: Either `answerable` or `unanswerable`
- `constraints`: Metadata filters applied at query time

## Metrics

### 1. Recall@K
Measures whether the *expected evidence* was retrieved within the top K results. 
- **Formula**: `(Number of Expected Chunks found in Top K) / (Total Number of Expected Chunks)`

### 2. Precision@K
Measures whether the *retrieved top K results* were actually expected.
- **Formula**: `(Number of Expected Chunks found in Top K) / (Total Retrieved Chunks up to K)`

### 3. Mean Reciprocal Rank (MRR)
Evaluates how high the *first* piece of expected evidence appeared in the ranking.
- **Formula**: `1 / (Rank of first expected chunk)`

### 4. Citation and No-Answer Checks
- **Citation Validity**: Checks whether the citations generated by the LLM (or mock generator) perfectly match the `expected_policy_ids`.
- **No-Answer Validity**: Ensures that queries marked as `unanswerable` correctly trigger the system's safe-fallback response.

### 5. Latency Tracking
Measures the monotonic elapsed time (`time.perf_counter()`) for:
- Retrieval phase
- Generation phase

*(Token usage and external costs are tracked where available. If they are not natively surfaced by the local/mock model, they are documented as N/A instead of fabricating estimates).*

## Evaluation Workflow

The evaluation runner compares three configurations side-by-side using the same test cases:
1. `vector`: The Part 3 semantic vector baseline
2. `hybrid`: The Part 4 RRF hybrid (Vector + FTS) baseline
3. `hybrid_rerank`: The Part 5 RRF + Cross-Encoder Reranker + Context Assembly

### Running the Evaluator
Run the evaluation CLI from the project root:
```bash
uv run python -m app.evaluation.runner
```

### Outputs
- **Scorecard**: `data/evaluation/scorecard.json` containing aggregated averages (MRR, Recall, Precision, Latencies).
- **Failure Log**: `data/evaluation/failure_log.json` containing detailed structured logs of where the pipeline fell short (e.g., recall failures, citation hallucinations).

## Known Limitations
- The expected evidence matching is strictly deterministic based on `chunk_id`. It does not use an LLM evaluator to judge "semantic sufficiency" of retrieved evidence if it happens to be an alternate, unlabelled chunk.
- Generating the test dataset manually is subject to human bias. True evaluation scaling requires mining real user queries.
